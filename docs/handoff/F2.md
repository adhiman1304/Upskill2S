# F2 handoff: identify a certification from free text (client half)

Status: done. `npm --prefix client run build` passes. `npm --prefix client run lint` reports 0 errors and 1 warning (the existing `react-hooks/exhaustive-deps` warning in `LibraryPage.tsx`). No server or Prisma files changed. Nothing is committed.

The server half is F's `POST /api/catalog/identify`, documented in `docs/handoff/F.md`. I built against the agreed contract first. I then checked it against F.md and F's code in `server/src/lib/contracts/catalog.ts` and `server/src/routes/catalog.ts`. The types and error codes match.

Where F.md's client spec differs from my brief:
- **Retired candidates:** a "Retired" badge plus the brief's wording. They show as one warning chip: "Retired, see <successorCode>", or "Retired" when there is no successor.
- **400 `OPENAI_KEY_INVALID`:** handled as F.md asks. It shows an error alert with the server message and an "Open settings" link.
- **Aborting:** F.md asks to abort when the query changes or the dropdown closes. The request is aborted when the query changes or is cleared, on Back or Escape, and on unmount. It is **not** aborted when the dropdown closes only because focus left it (switching windows also blurs the input). Otherwise looking away during a 40 s search would throw the work away. Refocusing the input shows the result.
- **Anthropic provider tile:** F.md suggests bringing it back on Home. I did not add it (scope was the search); see Left.

## Behavior

**Search dropdown:**
- Once the query has at least 3 trimmed characters and the catalog search for that query has returned, the last row is always "Can't find it? Ask the agent to identify it", with a lucide `Sparkles` icon.
- The row is not shown while a search is still in flight, so pressing Enter quickly on "dp-700" cannot trigger identify by accident.
- With zero hits, the row is the only option, so it is focused by default and Enter triggers it. A hint, "No match in the catalog yet.", sits above it.
- Below 3 characters the identify row never appears. The old empty text ("No certification matches …") still shows for short queries.
- The row is a `role="option"` in the same listbox as the hits. Arrow keys, Enter, hover and click work as they do for hits.

**Identify view (replaces the results inside the same panel):**
- **Loading:** a spinner with "Searching the web for '<query>'…" (the `.loading-state` style) and "This can take up to a minute."
- **Candidates:** each candidate is a listbox option, and arrow keys and Enter work. A row shows:
  - Provider logo, code, provider name, and a confidence chip: high uses `chip-passed`, medium `chip-accent`, low `chip-planning`. Screen readers hear "<level> confidence".
  - The title, and the note in muted text.
  - A warning chip, "Retired, see <successorCode>", or just "Retired" when there is no successor.
  - An "Official page" link that opens in a new tab and does not select the row.
- **Selecting a candidate:**
  - With `catalogMatch.certificationId` set, it navigates to `/certifications/:id`.
  - Otherwise it calls `resolveCertification` and then navigates. The call uses `catalogMatch.code` when present (the catalog's canonical code, as F's schema comments specify), otherwise the candidate's code.
  - A spinner shows on the row while it resolves. A resolve error shows below the list.
- **No candidates:** "The agent could not find a certification matching that. Try the official exam code, or describe it in Help me choose.", with "Help me choose" linking to `/intake`.
- **400 `OPENAI_KEY_INVALID`:** an error alert, "Your OpenAI API key was rejected.", with the server message and an "Open settings" link.
- **412 `OPENAI_KEY_MISSING`:** `KeyRequiredCallout` with the body "Identifying a certification runs with your own OpenAI key. Add it in Settings, then try again."
- **429 `RATE_LIMITED`:** a warning alert titled "Too many identify requests." Its body is the server's message, which includes the wait ("Try again in about N minutes").
  - `ApiError` does not expose the body's `retryAfterSeconds`, so the client relies on the message.
- **Any other error:** an error alert with the server message and a "Try again" button.
- **Back:** every identify view has "Back to catalog results". Escape does the same. Back cancels a running request.
- **Editing the query:** this returns to the normal results and aborts a running request. Closing the dropdown by blur does not abort; the result shows when the input is focused again. Re-triggering identify for the same query reuses the earlier result instead of spending another request. After an error it always asks again.

**Layout:**
- Desktop uses the existing dropdown width (680 px max).
- On mobile the arrow column is hidden, text wraps, and the callout's button wraps under the text and is 40 px tall.
- At 390 px: candidate rows are at least 40 px tall (measured 138 and 147 px), the back button is 40 px, and the document's `scrollWidth` is 390, so there is no horizontal scroll.

## Verified

I tested against the running dev servers, which I did not restart. I used the in-app browser at 1280 px, and a scripted headless Chromium at 1280×900 DPR 1 and at 390×844 DPR 2 with mobile emulation.

- **"anthropic claude accosiate":**
  - The fuzzy search now returns Anthropic CCA-F, and the identify row is the last row.
  - Triggering identify (ArrowDown then Enter, and also by click) shows the loading state.
  - The **real** server then returns 412, and the key callout renders with its link to `/settings`.
  - Before F's route landed it returned 404, which exercised the generic error and "Try again" path.
- **"zz":** no identify row.
- **"dp-700":** with the first row active, Enter navigates to `/certifications/cmvimifrs00017l5jbwya68qc`.
- **Nonsense query with zero hits:** "No match in the catalog yet." shows, the identify row is `aria-selected`, and Enter triggers it.
- **Mobile Home tabs:** Search, Mine and Providers still switch and update `?tab=`.
- **Success and empty states:** I could not test a real successful identification, because no OpenAI key is stored. I exercised these states by mocking only the identify response in the browser. The mock had a db-matched candidate and a retired candidate with a successor and a long title, plus an empty candidate list.
  - Rendering, wrapping at 390 px, and click-to-navigate on the db-matched candidate all worked.
  - The `resolve` path for a catalog-only candidate was not exercised (to avoid creating dev data). It uses the same `resolveCertification` call as catalog-only search hits.
- **429 and 400 `OPENAI_KEY_INVALID`:** verified by code against F's route only. Neither was triggered live.
